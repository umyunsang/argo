## 연구 문제

연구 자동화의 병목은 코드를 실행하는 능력보다 **무엇을·왜·어떤 조건에서 검증할 것인가**를 정하는 데 있다.
선행 층(전 과정 자동화, 가설 토너먼트, 지식 그래프 추론, 그래프 기반 맥락 전달)은 각각 중요하지만,
**설계 근거와 운영 병목이 같은 기록에 섞여** 남기 때문에 결과가 나빠졌을 때 가설의 문제인지 하네스의
문제인지 사후에 가릴 수 없다.

## 연구 대상 — 결합 방식의 설계

개별 기법의 신규 제안이 아니다. 네 갈래를 하나의 연구 루프로 잇는 **최적 구성을 실험으로 찾는 것**이다.

1. 지속형 REPL 기반 재귀 실행
2. 궤적 근거에 따른 하네스 상태 갱신
3. 격리 작업트리와 불변 커밋 기반 재현 실행
4. 의미 기반 문헌 검색

## 차별성 — 이중 refine의 계보 분리

연구 refine은 가설·조건·방법을, 엔진 refine은 하네스를 갱신하되 **두 이력을 덮어쓰지 않고 따로 보존**해
어느 쪽 변경이 결과를 바꿨는지 귀속한다.

## 검증 — 동일 모델·동일 예산의 제거 실험 4종

그래프 제거 · 설계 경쟁 제거 · refine 제거 · 단일 에이전트 베이스라인

사람 개입 횟수

## 승인 판정과 사전 고정

- GoalSpec(목표·권한) / HypothesisSpec(주장·영가설·메커니즘·반증 조건) /
  ProtocolSpec(표본·조건·변수·대조군·지표·반복 횟수·중단 규칙)
- 검사 축: 추적성·반증성·비교성·적법성·예산·실행성 → **ADMIT · REVISE · BLOCK**
- ADMIT된 ProtocolSpec은 실행 전 **엔진 버전과 함께 해시로 고정**해 그래프에 커밋한다.
- 실행 실패(비정상 종료·자원 부족·의존성 오류)는 반증 근거에서 제외한다.
- 설계 경쟁 우승안은 **별도 보류 데이터**에서 한 번 더 확인한다.

## 현장 구현 서약

> 사전 개발물은 반입하지 않고, 공개된 오픈소스 하네스를 기반으로 대회 기간 내에 구현한다.

무박 2일 범위: 컨텍스트 그래프 스키마 → 설계안 2건 경쟁과 admission → 1회 실행·판정 → refine 1회.
공개 과학 데이터만 사용한다.
