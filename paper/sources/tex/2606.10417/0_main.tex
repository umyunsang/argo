\begin{abstract}

% Most test quality metrics measure the implementation, not the specification. Developers rely on code coverage and mutation kill score to assess how thoroughly their tests exercise code under test. 
% Yet these metrics are fundamentally implementation-centric: coverage evaluates the proportion of source code executed, while mutation assesses assertion strength on covered code. Neither evaluates how the implementation aligns with its behavioural specification.
% This creates a gap between the specification and implementation, leaving documented behaviours untested despite high coverage or mutation kill scores.
% In this paper, we empirically demonstrate that this gap is consistently present across ten popular open-source Java libraries comprising 8,922 documented methods.
% Using our analysis, called \toolname{},  
% we estimate that at least 17\% of documented behaviours are not validated by existing test suites despite having high structural coverage. 
% Capturing behavioural completeness adds insight beyond structural metrics: 
% 85\% of untested behaviours occur in methods with over 90\% line coverage, and 50\% of untested behaviours occur in methods exceeding 90\% mutation kill score.
% These results establish behavioural coverage as a meaningful, currently under-measured,  dimension of test suite completeness that structural metrics alone cannot capture.

Traditional test adequacy metrics measure a system's implementation, not whether it adheres to its expected behaviour. 
While developers rely heavily on code coverage and mutation testing to assess test suite quality, these metrics are fundamentally implementation-centric and cannot detect gaps between
% documented intent and actual  validation. 
what the code is \textit{expected} to do and what it \textit{actually} does.
Unfortunately, there has been no way to reliably detect these discrepancies; in this paper we introduce an automated proof-of-concept approach to investigate these gaps. %, called \toolname{}.
The approach extracts expected method-level behaviours from natural language documentation and source code, maps them to existing test cases, and identifies gaps between \textit{expected} and \textit{validated} behaviours. 
We evaluate the approach across ten popular open-source Java libraries comprising 8,922 methods, extracting 20,729 behaviours with 93.1\% precision. 
Our empirical analysis conservatively estimates that 17.5\% of detected expected behaviours remain entirely untested, which we term as the test suite's \textit{behavioural gap}. 
To determine if these gaps are merely an artifact of human-driven testing, we evaluate state-of-the-art automated test generators 
(\textsc{EvoSuite} / \textsc{ASTER}), finding that they similarly fail to validate at least 20.6\% / 27.1\% 
of detected expected behaviours. We further demonstrate that behavioural gaps are not predicted by traditional structural metrics: the majority of untested behaviours occur in methods that already have high line coverage, and over half persist in methods with high mutation kill score. 
% We demonstrate that behavioural gaps are statistically independent of traditional structural metrics: 85.4\% of untested behaviours occur 
% within methods achieving $>$ 90\% line coverage, and 50.1\% occur within methods with 
% $>$ 90\% mutation kill scores.
These results suggest behavioural coverage acts as an independent dimension of test 
suite adequacy that can complement traditional structural metrics.
\end{abstract}
