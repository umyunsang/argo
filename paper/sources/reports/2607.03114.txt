Abstract
High-level languages such as R or Python are used frequently to
analyze and visualize data in the form of scripts or notebooks. How-
ever, these artifacts suffer from reproducibility issues due to what
we frame as implicit assumptions made by the authors. Such as-
sumptions range from package versions and shapes of involved data
tables, to manual and often undocumented setup steps. Within this
work, we provide a unified, example-driven perspective on implicit
assumptions in data analysis backed by an explorative proof-of-
concept implementation. With this perspective, we propose the use
of static analysis techniques to identify such assumptions and to
make them explicit in the form of code constraints, focusing on the
inclusion of data-analysis-specific issues. Such constraints can then
be used to automatically transform these scripts into executable and
reproducible artifacts, to check these assumptions at runtime, and to
serve as documentation to support code reuse and comprehension.

1 Introduction
There are many high-level data-analysis languages such as R, Python,
MATLAB, and Julia which offer a sophisticated range of features
for statistical tests and visualization [38, 10, 24]. Additionally, these
languages benefit from notebook environments such as Jupyter
Notebook [12] or Quarto [1], which support an interactive explo-
ration and manipulation of data. These technologies support domain
experts in conducting their analyses without training in software
engineering principles [35]. In practice, however, analysis scripts [31,
28] and notebooks [15, 22, 26] suffer issues in reproducibility and
structure [30]. Various studies show that they lack executability [31,
22, 26, 15] and hence reproducibility. These studies reveal that 65 %
to 77 % of the analyzed artifacts fail to execute due to missing de-
pendencies, wrong execution order, or bad coding practices [31].
Moreover, research on code reuse in data science finds that 70 %
to 80 % of the analyzed code snippets are clones of other snippets
with 50 % containing no unique code at all [2, 16]. Code reuse is even
more prevalent across different projects. This indicates significant
reproducibility issues of data science code. Such artifacts are used
frequently to help other researchers understand the applied methods
and the steps conducted in the accompanied publication or to reuse
parts within their own related analyses [17, 2]. Reasons for these
difficulties are manifold. Ranging from finding the used versions of
packages and the language, to external dependencies like resource
files. Additionally, they may rely on previous steps or expect the
dataset to have a specific shape [31]. While there is already some
research on improving the reproducibility of data science scripts and
notebooks, there is not yet a unified view on the various challenges
that arise when trying to reproduce, replicate, or reuse these artifacts.
In this work, we address this by framing these difficulties as implicit
assumptions, similar to classical software development [18]. Addi-
tionally, we propose the systematic use of static analysis techniques
to identify and document these implicit assumptions in the form of
constraints, e.g., by using abstract interpretation to infer the values of
variables [5, 8]. Such an analysis may happen either in the context of
the original analysis environment (cf. [9]) or retroactively when a re-
searcher tries to reproduce, replicate, or reuse the artifact. The results
can then be used to add checks to the program that serve as an explicit
documentation and as a dynamic validation for each run of the script.
Within the rest of this paper, we use the R programming language as
a primary example to illustrate specific cases. Furthermore, we use it
as a basis for an explorative proof-of-concept implementation of our
idea on top of flowR, a static program analysis framework for R [29].
However, the proposed approach and most of the challenges are
inherent to data analysis and hence language-agnostic. Therefore,
we include a brief overview of the generalizability of the approach.
Finally, we conclude with the implications of our work as well as a
list of next steps in Sections 4 and 5.
2 Related Work
To address issues of non-executable or non-reproducible research,
several solutions have been proposed (cf. [27, 9]), including tools to
gather executable code versions [13], recreate the execution order of
notebook cells [36], provide linting recommendations [23], infer the
environment of Python code [14, 41], and restore the execution en-
vironment of notebooks [37]. Yet, neither do these tools address the
potential interactions between assumptions, such as the version of
an interpreter restricting the available libraries, nor do they provide
a systematic approach to document these assumptions in the artifact.

One widely used technique for inferring code constraints is abstract
interpretation introduced by Cousot et al. [5]. It can be used to au-
tomatically infer preconditions on the code [4] and statically check
code contracts [19, 11], for example, to infer shapes of input data
for data science scripts [34, 33]. Additionally, subsequent research
by Pavle et al. presents a general static analysis framework for data
science notebooks [21]. Furthermore, Negrini et al. propose a static
analyzer for data transformations in Jupyter notebooks [20] and
Dolcetti et al. introduce a high-level linter to identify code smells in
data science scripts [8]. However, none of these approaches focus on
identifying and documenting issues of reproducibility, but instead
they target the detection of code smells and visualization errors.
3 Constraint Inference
This section explains our core idea of using constraint inference to
identify implicit assumptions in data analysis scripts. We propose
to differentiate between two scenarios for constraint inference: A
preemptive analysis in the context of the original execution environ-
ment with the original data available, and retroactive analysis when
aspects of the original execution environment may be unknown
or the original data may only be partially available. In the former
case, the researcher may want to ensure that the analysis script is
self-contained and complies with the fair principles [39]. This case
is usually easier as we can use the current computing environment
to infer package versions and the shape of used datasets [9]. For the
latter case, we differentiate between three scenarios which benefit
from the identification of implicit assumptions in research artifacts.
A researcher may want to:
(1) Reproduce the results of the original study.
(2) Replicate the results with a different dataset.
(3) Reuse parts within a different but related context [39].
We use this section to introduce the general idea with a running exam-
ple (3.1) and discuss the challenges alongside sketches of potential so-
lutions of common assumptions like inferring package versions (3.2),
script interdependencies (3.3), and data shape expectations (3.4).
3.1 Running Example
Consider the following example R script which reads a dataset from
a csv file (L2), calculates a mean score (L5) grouped by age (L4),
conducts a t-test (L6), and plots the results (L7, L8). This follows
the common data analysis workflow outlined by Wickham [38]. Al-

structure of data analysis scripts:

Some assumptions, like A10, are silent, meaning that they do not
cause visible errors when violated but cause incorrect results, while
others, like A2, can lead to runtime errors or warnings. However,
they do not have to cause errors. For example, newer versions of
ggplot2, dplyr, or R may introduce changes in aesthetics, handling
of edge-cases, value coercion, or deprecated functions, which can
lead to different results. Although it may be easy to identify these
assumptions in the 8 example lines, this gets much harder for real-
world scripts [28]. In the context of our simple example, a preemptive
analysis can get the exact version of used packages, knows whether
data.csv exists, the shape of the data, and more, just by reading the
information from the environment and executing the script. In con-
trast, a retroactive analysis is limited to inferring constraints about
which package versions could have been used and what the data
might have looked like. Yet, this can still be important in detecting
conflicts or reconstructing executable environments for the analysis.
3.2 Inferring Package Versions (A1–A3)
Incorrect versions are one of the main issues in reproducing data
analyses [3]. There is a wide range of solutions that help to collect
the used package versions and their dependencies preemptively.
2
Yet, work on reconstructing such information retroactively is rare
and either tries to obtain all package versions available at a given
time [3] or analyze the API usage in notebooks [37]. Currently, there
exists no advanced and holistic approach to retroactively infer pack-
age versions using all of these information sources combined and
document them in a machine readable format.
• 
Problem Statement. Given an analysis artifact, combined with
the available evaluation data and meta information, generate the
requirements for the computing environment. These requirements
include the required packages, their versions, and indirect dependen-
cies such as system libraries. If the original computing environment
is available, this can be inferred preemptively [9]. Hence, the main
challenge is to infer these constraints retroactively.
• 
Proposed Solution. To reconstruct the computing environment,
we use a three-step approach: (𝑖) identify all dependencies required

constraint for ggplot2 based on the use of geom_count (A1). Incor-

constraint, requiring different versions based on the used version of
R (A3). To infer package versions, we are currently working on adding

this strategy, we can build a constraint system describing all possi-

system can be enriched with additional information, such as a date
range in which the study was conducted. If this process yields only
a single combination of possible versions and their dependencies,
we can use these to generate a corresponding virtual environment.
If multiple sets are possible, we can use the constraints to generate
a set of possible environments to reproduce the analysis. This can
then be combined with dynamic analysis, comparing the execution
results, to identify the most likely environment fully automatically.
• 
Generalization. Assumptions like A1–A3 are also common prob-
lems in other programming languages such as Julia or Python. How-
ever, inferring the package versions is not only useful in hindsight.
These techniques can also be applied in the context of the original
computing environment or in scenarios where a machine-readable
format of the computing environment is available. In such cases,
the constraints can be used to check the compatibility of the stated
requirements with the actual environment and uncover conflicts in
the used API.
3.3 Script Interdependencies (A4 and A7)
Usually, research artifacts rely on multiple scripts or notebooks to
conduct all of their analyses. However, similar to how individual
notebook cells may depend on each other [13], these scripts tend to
have implicit dependencies on each other. One script may produce
the data that another script consumes (e.g., A4), or clean the existing
data as a side-effect. In a language like R, scripts can even pass on
variables if they are sourced in the same session. This can lead to
cases like the use of grouped in the running example (3.1) which
is not defined in the script itself (e.g. A7). While there exist some
rudimentary solutions which identify global variables,

restricted to single sources and do not incorporate any potential
script interaction, files, or package dependencies. Similarly, while
common notebook formats like Jupyter Notebooks or RMarkdown
store the last output of a cell, they offer no way to automatically
record artifact-wide relations or necessary re-executions of cells.
• 
Problem Statement. Given an analysis artifact and the available
execution environment (3.2), identify implicit dependencies between
the scripts and their code. Such dependencies may be enriched with
the information about which scripts need to run within the same
environment. Then, using these constraints, identify all potential
execution orders, and their interactions. This is especially important
in the case of ambiguity, in which a number of either scripts or cells
could be executed first, but their effect on the global state is different.
• 
Proposed Solution. To identify dependencies between these scripts
in the retroactive case, we propose a two-step approach. First, we
build the program dependency graph of each script independently
but follow explicit script inclusions (e.g.,source calls). With this, we
automatically gain information about explicit dependencies, poten-
tially undefined values and functions, globally defined identifiers,
and files which are either written or read by the scripts. In the second
step, we can use this information to create links between scripts. This
also connects previously undefined variables and function calls with
definitions of their identifiers, the loading of libraries to imported
functions, library loads to their installation (3.2), and file reads with
their creation. The resulting graph indicates:
(1) Scripts without any implicit dependency on or to other scripts.
Such scripts may be executed completely independently.
(2) Scripts that may depend on other scripts. Those scripts should be
executed before their dependents. The possible execution orders
are the topological graph orderings.
(3) Scripts that still have global variables or functions which are
undefined, or that read or write files that do not exist.
Granularity wise, this can also be applied to code cells in notebooks
or even individual code-blocks such as function definitions. We have
started to implement this approach in flowR [29] and evaluated it
on 8,160 real-world R projects scraped from Zenodo, Havard Data-
verse, JSS, and Figshare, with a total of 33,336 files. With this, we
find that 14.6 % of projects contain implicit interdependencies. In
the preemptive case, these dependencies can be solved by recording
the execution order, including re-executions. Existing tools such as
historyAsScript,
4 
fail to incorporate project-wide dependencies
or multiple sessions. Hence, we propose to extend these tools to
incorporate a project-wide view of the dependencies.
• 
Generalization. The concept of interdependencies of research
scripts (assumptions like A4 or A7) or notebooks exists for every gran-
ularity and essentially every language in the form of a reliance on
external state like the connection to a database. Detecting such poten-
tial interdependencies is also helpful to ensure that an analysis does
not rely on the execution order of the scripts or any external state.
3.4 Data Shape Expectations (A5, A6, A8–A10)
In the real world, no data analysis artifact contains any kind of “unit
tests” and quality assurance is rare [28, 35]. Similarly, these scripts al-
most never validate that loaded data conforms to the expected shape.

They simply access the columns they “know” or expect to exist (A8)
and assume that the data is in the correct format (A6). Some of these
assumptions are checked implicitly by the language or function that
is called. However, there is no way to detect that, for example, an as-
signment intends to overwrite a column, that two measurements are
assumed to be independent, or that the values should follow a normal
distribution. Some explorative work already tries to leverage abstract
interpretation to infer series types to detect high-level errors like the
wrong plot type [8], and to infer types for visualization [40]. More
recent work also focuses on the dynamic postulation and verification
of statistical assumptions, indicating the relevance of this work [32].
Yet, there is no sophisticated approach to infer such implicit assump-
tions statically from the artifact itself and express them explicitly.
However, such guards are integral to support the reuse of analysis
artifacts in different contexts (e.g., newer versions of the dataset).
• 
Problem Statement. Take an analysis artifact including all avail-
able files and infer the constraints that loaded datasets have to fulfill.
Then, semi-automatically insert checks into the artifact to dynam-
ically ensure that the loaded data conforms to the expected shape.
• 
Proposed Solution. We propose using a new set of abstract do-
mains [6] to infer and track the shape of the data as it is loaded and
manipulated by the scripts. This includes the identification of the
data shapes (e.g., the number and names of the columns and their
types), the constraints on the data (e.g., that values must be unique or
follow a normal distribution), and the functions used with the data.
This way, we can infer the expectations of functions, such as the
requirements for a t-test (A10) or expected data shapes (A5), and add
guards to the artifact to dynamically ensure that the preconditions
and expectations are met. Moreover, we propose a semi-automatic
approach to add additional constraints that can not be inferred di-
rectly from the data, but that a researcher may add in a preemptive
scenario (e.g., that the result of a function must lie within a given
interval). So far, we added a data frame shape inference using ab-
stract interpretation to flowR. We define an abstract domain to track
column names, the number of columns, and rows of data frames.
For this, we map concrete data frame functions to a set of abstract
operations. A first evaluation of the implementation shows promis-
ing results for tracking the shape data in analysis scripts. Yet, this
requires a careful study of common functions to identify useful con-
straints that can be inferred from the data and the analysis artifact.
Additionally, not every constraint can be directly inferred from the
data (e.g., the independence of two measurements).
• 
Generalization. Expectations on the shape of data are frequent
and neither limited to data analysis nor to R [20, 32] sharing similar-
ities to, e.g., taint tracking and type inference. Inferring the shape of
data by tracking a known state and the operations on the data, can
be applied to most scenarios which involve external data that may
change over time. Similarly, the inferred constraints can also help
with comprehension, e.g., by uncovering unexpected requirements.
4 Conclusion
Within this work, we introduce the idea of implicit assumptions as
a novel, unified perspective on the difficulties in reproducing, repli-
cating, and reusing data analysis artifacts. Based on this perspective,
we envision a set of techniques to address these difficulties with the
help of static code analysis, and to enrich these artifacts with the
necessary information to dynamically ensure their reproducibility
and reusability. We combine this with an explorative implementation
on top of flowR which underlines the feasibility of our approach. Yet,
these categories are by no means exhaustive. For example, research
artifacts may rely on undocumented, manual setup steps or interac-
tivity from the user, which hinder automated execution, and reduce
the reproducibility of the results. Furthermore, such techniques are
no universal solution as inferring these implicit assumptions is in-
herently limited by Rice’s theorem [25]. Hence, we require thorough
analyses of reproducible and irreproducible artifacts to identify com-
mon patterns to use as heuristics for these techniques. Additionally,
we need to consider a human-in-the-loop approach if the detection of
an implicit assumption works, but can not be automatically resolved.
However, even in these cases, we believe that the mere detection
of implicit assumptions is still a valuable contribution, offering an
interesting and valuable research direction.
5 Future Plans
So far, we have already started working on a proof-of-concept im-
plementation of our idea on top of flowR [29] and intend to complete
this implementation by adding best-effort support for the detection
of all implicit assumptions mentioned in Section 3. To allow for ad-
ditional constraints by users, we intend on adding a combination
of a domain-specific language and the ability to detect violations of
common assumptions as with stopifnot in R. Subsequently, we
plan to evaluate the usefulness of our approach in three ways:
• Take non-executable artifacts from public repositories and pub-
lished studies (e.g., those found by Trisovic et al. [31]) and check
how many of them can be made executable with our approach,
comparing this to the related work (cf. [31, 15, 9]).
• Take executable artifacts and use fuzzing on their datasets to
produce problematic and unproblematic variations and to get an
understanding of the effectiveness of the inferred constraints to
prevent problems in reusing the artifact with different data.
• Conduct a user study with R users to evaluate the usefulness of
the inferred constraints as documentation for understanding and
reusing the artifact by measuring their performance in understand-
ing and reusing the artifact with and without the constraints.
