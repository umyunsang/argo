### Research Report: An Evaluation of Prompt Caching for Long-Horizon Agentic Tasks

#### 1. Authors and Institution(s)

The authors of this research paper are Elias Lumer, Faheem Nizar, Akshaya Jangiti, Kevin Frank, Anmol Gulati, Mandar Phadate, and Vamse Kumar Subbiah. All authors are affiliated with PricewaterhouseCoopers, U.S.

#### 2. How This Work Fits into the Broader Research Landscape

The field of Large Language Model (LLM) agents has advanced to enable complex, multi-turn, and long-horizon tasks that often require extensive tool calling. These agentic workloads frequently involve conversations spanning dozens of API calls and utilizing increasingly large context windows, which can accumulate tens of thousands of tokens. This escalating context size contributes to significant operational costs and increased latency in LLM applications.

To mitigate these challenges, major LLM providers such as OpenAI, Anthropic, and Google have implemented prompt caching mechanisms. Prompt caching reuses previously computed key-value (KV) tensors from attention layers, thereby reducing redundant computation for repeated prompt prefixes. While KV cache optimization has been a subject of research, focusing primarily on inference-level memory management and compression techniques like PagedAttention or selective retention of important tokens, the practical benefits of provider-managed prompt caching features for real-world agentic workloads remain underexplored in academic literature.

Existing work has included audits of prompt caching across providers, primarily to detect timing side-channel vulnerabilities. However, these studies typically utilized synthetic prompts and older model generations, and did not quantify cost savings, compare different caching strategies, or evaluate their impact on latency for modern, long-running agentic tasks. Consequently, there has been a gap in understanding how prompt caching performs and how it can be optimally configured within the dynamic and extensive contexts characteristic of agentic systems.

This paper addresses this gap by conducting a comprehensive evaluation of prompt caching specifically for long-horizon agentic tasks. It aims to quantify the cost and latency benefits across leading LLM providers and compare various caching strategies, thereby providing empirical data and practical guidance for the deployment of LLM agents.

#### 3. Key Objectives and Motivation

The motivation for this research stems from the growing complexity and operational demands of modern LLM agentic applications. As LLM agents take on increasingly sophisticated tasks, such as deep research, coding assistance, and autonomous task completion, they generate multi-turn conversations that involve numerous API calls and dynamically expanding context windows. This leads to two primary operational challenges: substantial API costs due to processing large volumes of tokens repeatedly, and increased latency, which degrades user experience.

Major LLM providers have introduced prompt caching as a feature designed to alleviate these issues by re-using computations for common prompt prefixes. However, the extent to which these provider-managed caching features deliver benefits in the context of dynamic, tool-intensive agentic workflows has not been systematically evaluated. The unique characteristics of agentic tasks, where conversation history and tool results introduce dynamic content, complicate the application of simple prefix caching.

Given this context, the key objectives of this research were:

1.  **Quantify Cost Savings**: To measure and quantify the reduction in API costs achieved through prompt caching when applied to long-horizon agentic tasks across multiple major LLM providers (OpenAI, Anthropic, Google) and their flagship models.
2.  **Evaluate Latency Improvements**: To assess the impact of prompt caching on latency, specifically focusing on the Time to First Token (TTFT), which directly reflects the speed of initial response generation, within agentic workflows.
3.  **Compare Caching Strategies**: To systematically evaluate and compare the performance of different prompt caching strategies:
    *   **Full Context Caching**: Representing a naive approach where the entire prompt is subject to automatic caching.
    *   **System Prompt Only Caching**: Focusing on caching only the static, reusable initial instructions given to the agent.
    *   **Exclude Tool Results Caching**: A more granular approach that strategically excludes dynamic and session-specific tool invocation outputs from the cached prefix.
4.  **Analyze Influencing Factors**: To conduct an ablation study investigating how prompt caching benefits scale with key workload characteristics, specifically prompt size and the number of tool calls within a session.
5.  **Provide Practical Guidance**: To derive actionable recommendations and nuanced guidance for practitioners implementing prompt caching in production-grade LLM agentic systems, considering provider-specific behaviors and optimization goals.

#### 4. Methodology and Approach

The research employed a structured experimental methodology to evaluate prompt caching across various LLM providers and caching strategies.

**4.1. Experimental Setup**
The evaluation involved three major LLM providers: OpenAI (GPT-5.2, GPT-4o), Anthropic (Claude Sonnet 4.5), and Google (Gemini 2.5 Pro). All selected models supported prompt caching via their respective APIs.

The benchmark utilized was DeepResearch Bench, a multi-turn agentic benchmark designed for tool-intensive workflows, featuring 100 PhD-level research tasks requiring web search tool calls. The research agent was implemented using Deep Agents, an open-source library. Each agent session began with a unique research question and iteratively used a web search tool before synthesizing a response. This setup aimed to simulate realistic agentic workloads where context windows grow dynamically.

For each model and cache condition, 40 independent agent sessions were conducted. Each session used a 10,000-token system prompt containing detailed agent instructions. Sessions commenced with a fresh context to ensure cache benefits were measured within individual multi-turn conversations rather than across different sessions.

**4.2. Cache Mode Implementation**
Four distinct cache conditions were implemented to control cache boundaries, primarily using Unique Identifiers (UUIDs) to explicitly break the cache at specific points:

*   **No Cache (Baseline)**: A UUID was prepended to the system prompt, preventing any prefix matching and forcing full recomputation for every request. This condition served as the baseline against which caching benefits were measured.
*   **Full Context Caching**: No UUIDs were added, allowing the provider's automatic caching mechanisms to operate on the entire prompt prefix. This represented a naive approach to enabling caching.
*   **System Prompt Only Caching**: A UUID was appended to the end of the static system prompt. This ensured that only the system prompt, which remains consistent, was cached, while dynamic conversation history, tool calls, and tool results were recomputed.
*   **Exclude Tool Results Caching**: UUIDs were appended after the system prompt and also after each tool result. This strategy aimed to prevent dynamic and session-specific tool results from being cached, thereby avoiding cache writes for content unlikely to generate future cache hits.

**4.3. Evaluation Protocol**
Two primary metrics were measured across all conditions:

*   **API Cost**: Calculated by multiplying the reported token counts (standard input, cached input, cache creation tokens) by the corresponding provider pricing (detailed in Appendix A, Table 3). Costs were aggregated across all API calls within a session.
*   **Time to First Token (TTFT)**: Measured using streaming responses, recording the duration from request initiation to the receipt of the first response chunk. This metric was chosen for its relevance in capturing latency improvements resulting from skipped prefill computation on cached tokens.

Before each experimental condition, warmup calls were executed to prime the cache, and cache creation tokens were recorded separately. A waiting period exceeding 24 hours was observed between different cache mode conditions to ensure cache entries expired according to provider TTL policies, preventing contamination between experiments.

**4.4. Statistical Analysis**
Independent samples t-tests were used to compare each cache condition against the no-cache baseline. Statistical significance was set at an alpha level of 0.05. For each model and cache mode, the mean cost, mean TTFT, percentage improvement relative to baseline, and p-values were reported. The sample size for each condition was n=40.

**4.5. Ablation Study**
An ablation study was conducted to investigate the sensitivity of caching benefits to:
*   **Prompt Size**: Evaluated across six sizes: 500, 2,000, 5,000, 10,000, 20,000, and 50,000 tokens. The 500-token condition served as a control, falling below typical minimum caching thresholds (1,024-4,096 tokens).
*   **Tool Call Count**: Evaluated across five counts: 3, 5, 10, 20, and 50 tool calls per session.
Median cost and TTFT were measured for each configuration across relevant cache strategies.

#### 5. Main Findings and Results

The evaluation yielded several key findings regarding prompt caching in long-horizon agentic tasks.

**5.1. Overall Benefits of Prompt Caching**
Across all four models tested (GPT-5.2, Claude Sonnet 4.5, Gemini 2.5 Pro, GPT-4o), prompt caching resulted in statistically significant improvements (p < 0.05) in both API cost and time to first token (TTFT). Cost reductions ranged from 41% to 80%, while TTFT improvements varied from 6% to 31%.

**5.2. Cost Reduction**
Prompt caching consistently delivered substantial API cost reductions across all providers and cache strategies.
*   GPT-5.2 demonstrated cost reductions of 79-81%.
*   Claude Sonnet 4.5 showed 78-79% savings.
*   GPT-4o achieved 46-48% reductions.
*   Gemini 2.5 Pro exhibited 28-41% savings.
The consistency of these cost savings across different strategies suggests that caching the large, stable system prompt is the primary driver of cost benefits, with additional caching of dynamic conversation history or tool calls providing only marginal incremental advantages in the experimental setup.

**5.3. Time to First Token (TTFT) Improvements**
Latency improvements, measured by TTFT, showed greater variability across providers and strategies compared to cost savings.
*   GPT-4o achieved 28-31% TTFT improvement with the "System Prompt Only" and "Exclude Tool Results" strategies. However, "Full Context Caching" resulted in a slight TTFT regression of 8.8%, indicating that caching dynamic content can introduce overhead.
*   Claude Sonnet 4.5 demonstrated consistent TTFT improvements across all cache strategies, ranging from 20.9% to 22.9%, suggesting differences in how providers handle dynamic content caching.
*   GPT-5.2 showed a 13.0% improvement with the "Exclude Tool Results" strategy.
*   Gemini 2.5 Pro achieved a 6.1% improvement with "System Prompt Only" caching.
TTFT measurements exhibited natural variance influenced by factors such as server load and network conditions.

**5.4. Cache Strategy Comparison**
*   **Cost Optimization**: For cost, all three caching strategies (Full Context, System Prompt Only, Exclude Tool Results) provided similar benefits within each model, typically within 2-4 percentage points. This reinforces that the system prompt, which is cached in all these strategies, contributes most to cost savings.
*   **Latency Optimization**: The choice of cache strategy had a more pronounced impact on TTFT. "System Prompt Only" and "Exclude Tool Results" caching consistently outperformed "Full Context Caching." In some cases, "Full Context Caching" showed no improvement or even slight regression in TTFT, which is attributed to the overhead of writing caches for dynamic content (e.g., tool calls and results) that is unlikely to be reused across sessions.

**5.5. Strategic Cache Boundary Control**
The results indicate that explicitly controlling cache boundaries is crucial for maximizing prompt caching benefits in agentic workloads. Since providers often automatically trigger cache creation, unmanaged caching can include dynamic, session-specific content, leading to cache write overhead without corresponding read benefits. The most effective strategy involves caching only stable, reusable content, such as the system prompt. Dynamic values like timestamps, session identifiers, or user-specific information embedded within the system prompt should be placed at the end to maximize the cacheable prefix. Similarly, dynamic function calling where tool definitions change between requests can invalidate cached prefixes; maintaining a fixed set of general-purpose functions or leveraging code generation over traditional function calling for dynamic capabilities can mitigate this.

**5.6. Tool Call Caching Considerations**
While caching tool calls and results might seem beneficial for long-running sessions, its utility is limited. Cache creation incurs overhead, which is only amortized if the cached content is reused. Tool calls that produce variable results or are unlikely to be repeated offer no caching benefit and may introduce overhead. Furthermore, common context management techniques like summarizing or pruning old tool calls can break cached representations, making tool call caching counterproductive.

**5.7. Provider Implementation Variability**
Provider implementations of prompt caching differ in key aspects. Minimum token thresholds for cache eligibility range from 1,024 to 4,096 tokens. Time-to-live (TTL) durations vary from 5 minutes to 24 hours. Some providers offer automatic caching, while others require explicit API parameters. These differences necessitate consulting current provider documentation and conducting workload-specific experiments to optimize caching strategies. The study also noted that prompt caching can introduce timing side-channels, raising security considerations.

**5.8. Ablation Study Results**
*   **Ablation by Prompt Size**: Cost savings scaled linearly with prompt size and were universally positive for sizes above provider-specific minimum thresholds. For instance, at 50,000 tokens, GPT-5.2 achieved 89% cost savings, Claude Sonnet 4.5 achieved 88%, and GPT-4o 54%. TTFT improvements were also most pronounced at larger context sizes, with GPT-4o showing a 60% improvement at 50,000 tokens. For prompts below the minimum caching threshold (e.g., 500 tokens), modest cost savings were observed, but TTFT regressions (10-18% for some models) occurred as caching could not activate.
*   **Ablation by Tool Count**: Cost savings remained consistent across varying numbers of tool calls (3 to 50), typically within a 10-percentage-point range. This indicates that the number of tool calls did not substantially affect the cost benefits of prompt caching. TTFT results for tool count ablation showed higher variance; while GPT-4o maintained consistent TTFT improvements, Claude Sonnet 4.5 exhibited diminishing returns at higher tool counts (e.g., from 19% improvement at 3 tools to 5% at 50 tools), likely due to server load fluctuations during experiments.

#### 6. Significance and Potential Impact

This research provides a comprehensive and quantitative evaluation of prompt caching for long-horizon agentic tasks, addressing a notable gap in the existing literature. By systematically comparing caching strategies across major LLM providers and flagship models, the study delivers empirical evidence of the substantial benefits of prompt caching.

The findings demonstrate that prompt caching significantly reduces API costs (41-80%) and improves latency (13-31% TTFT) in agentic workflows. This has direct and substantial practical implications for the deployment and operational efficiency of LLM agents in production environments. The guidance on strategic cache boundary control—prioritizing caching of stable components like system prompts, strategically placing dynamic content, and avoiding caching of volatile tool results—provides actionable recommendations for practitioners. These strategies can prevent unintended performance degradation that naive full-context caching might introduce.

Furthermore, the ablation study clarifies that prompt size is a more dominant factor in driving caching benefits than the number of tool calls. This insight can inform prompt engineering practices, encouraging the maximization of stable system prompt length within architectural constraints. The identification of provider-specific behaviors, such as minimum token thresholds and varying handling of dynamic content, underscores the need for tailored implementation approaches and direct experimentation for specific workloads.

Overall, this work contributes to the advancement of efficient LLM agent deployment, enabling developers and organizations to reduce operational costs, enhance user experience through faster response times, and build more robust and scalable agentic systems.
