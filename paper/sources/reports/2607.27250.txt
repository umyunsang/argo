## Research Report: Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories

### 1. Authors and Institution(s)

Prakhar Khatri is listed as an independent researcher, with contact information provided as prakharkhatri123@gmail.com.

### 2. How This Work Fits into the Broader Research Landscape

The development of AI coding agents capable of automating software engineering tasks is an active area of research. Benchmarks such as SWE-bench (Jimenez et al., 2024) have established paradigms for evaluating these agents, often focusing on their ability to resolve real-world issues by producing pull requests. Subsequent work, including studies on agent–computer interfaces (Yang et al., 2024), has demonstrated that factors like harness design (e.g., tool ordering, context budgets, retry logic) can significantly influence agent performance, independent of the underlying language model.

A critical component of guiding AI coding agents in real-world software development is the provision of repository-level context, often in the form of dedicated "context files" like `AGENTS.md` or `CLAUDE.md`. These files are designed to provide agents with coding conventions, architectural constraints, and workflow guidance, with the expectation that this information will lead to improved code generation. Platforms like Claude Code have integrated the auto-loading of such files, and practitioners invest resources in authoring them.

However, empirical evidence regarding the effectiveness of these context files has been contradictory. Prior studies have yielded conflicting results: Lulla et al. (2026) reported that `AGENTS.md` files improved agent efficiency (reduced wall-clock runtime and fewer output tokens) for Codex-family agents, while Gloaguen et al. (2026) found no significant effect on task completion correctness for Claude-family agents. These discrepancies have been attributed to differences in the agents studied, evaluation methodologies, and experimental controls, making a direct reconciliation challenging without a controlled study that systematically varies context injection strategies across different agent families.

Beyond static context files, the broader field of LLM agent research explores various forms of persistent memory systems, including operating-system-style memory management (Packer et al., 2023), session-accumulated skill libraries (Wang et al., 2023), and agent loops that integrate reasoning, acting, and self-reflection (Yao et al., 2023; Shinn et al., 2023). Research by Liu et al. (2024a) also indicates that models may utilize information unevenly within long prompts, potentially underusing material placed mid-context. Related work on retrieval-augmented generation (RAG) (Lewis et al., 2020) has been applied to code tasks, focusing on retrieving relevant files, functions, or documentation (Zhang et al., 2023; Ding et al., 2023; Liu et al., 2024b; OpenAI, 2024). While these efforts primarily concern *what* context to retrieve at query time, `AGENTS.md` files represent a static, author-curated context layer. This paper specifically investigates the utility of this static context layer.

Methodologically, this work also incorporates equivalence testing, a statistical approach (Schuirmann, 1987) that allows for claims about the absence of an effect within specified bounds, in contrast to traditional null-hypothesis testing which cannot confirm a null. This methodology, alongside permutation tests and power analysis, aligns with recommendations for empirical software engineering (Wohlin et al., 2012).

### 3. Key Objectives and Motivation

The primary objective of this research is to empirically investigate whether the strategy by which repository context is injected into AI coding agents affects their performance, specifically in terms of task correctness and efficiency. This study aims to conduct a controlled ablation of context-injection strategies across different agent architectures to provide clarity on the efficacy of common practices.

The motivation for this work is multi-faceted:

*   **Ubiquity of Context Files:** `AGENTS.md` and similar project-level guides have become a standard part of the infrastructure for AI coding agents. Developers invest significant effort in authoring these files, anticipating that they will lead to the production of higher-quality code by the agents.
*   **Contradictory Empirical Evidence:** As noted in the broader research landscape, prior studies have yielded conflicting results regarding the impact of these context files on agent performance. One study suggested efficiency improvements, while another found no significant effect on task completion. These conflicting findings, stemming from differences in agents, evaluation methods, and experimental controls, created a need for a unified, controlled study to reconcile these observations.
*   **Understanding Mechanisms of Agent Failure/Success:** Beyond simply measuring an effect, the research aims to understand *why* context files might or might not be effective. This involves a detailed analysis of agent failure modes to determine if failures stem from a lack of repository knowledge (which context files could supply) or from other factors like implementation skill.
*   **Guidance for Practitioners:** By evaluating the impact of context files, the study seeks to provide actionable insights for practitioners who are authoring these guides and for platform developers who are designing systems for AI coding agents. If context files are found to be ineffective for certain aspects of performance, it suggests that developer effort might be more effectively directed elsewhere.
*   **Methodological Refinement:** The study also implicitly aims to highlight methodological considerations for evaluating AI coding agents, such as the importance of agent-specific task screening and the statistical power required to detect subtle effects, especially when claiming the absence of an effect (bounded null).

In summary, the key objectives are to:
1.  Quantify the impact of different context-injection strategies on coding agent correctness and efficiency.
2.  Identify the underlying reasons why context injection might or might not affect performance through failure-mode analysis.
3.  Reconcile existing contradictory findings in the literature by conducting a controlled, multi-agent study.
4.  Derive practical implications for the design of context files and agent development workflows.

### 4. Methodology and Approach

#### 4.1 Overview

The study employed a controlled ablation design to investigate the impact of context-injection strategies on coding agent performance. The independent variable was the context-injection strategy, with three levels: NONE, ALWAYS ON, and SELECTIVE. Two frontier coding agents (Claude Code and Codex) were utilized. Performance was measured by binary task correctness (pass/fail against gold tests) and various efficiency metrics. Each task was run under all three strategies with three independent repeats, forming a within-task paired design. A total of 291 agent runs were completed, with 288 runs successfully evaluated for correctness.

#### 4.2 Task Selection and Evaluation

*   **Repositories:** Approximately 40 GitHub repositories were initially surveyed from various sources, including existing studies. Selection criteria included: presence of exactly one root `AGENTS.md` file without competing instruction stacks, `AGENTS.md` quality rated "Good" or "Excellent" using a structured rubric (covering build/test/style conventions, architectural guidance, specificity), feasible setup (not oversized monorepos), and Python-only to avoid language-specific confounds. This process narrowed the selection to three repositories: `pdm` (package manager, 477-word context file), `firebase-admin-python` (cloud SDK, 1236-word "Excellent" rated file), and `opshin` (domain-specific compiler, 248-word file). These repositories represented distinct domains and `AGENTS.md` quality levels.
*   **Tasks:** Tasks were extracted from merged pull requests via the GitHub API. The PR description served as the agent prompt, the base commit as the starting state, and the PR's own test files as the gold evaluation. Tasks were filtered to include those that added or modified test files (required for gold-test scoring), were non-trivial (multiple files or >50 lines of code), and did not require external credentials or services. An initial batch of 12 tasks (4 per repository) was generated. To avoid floor/ceiling effects, a Codex screening sweep over 84 candidate tasks (3 strategies × 1 repeat) was conducted to identify tasks within a "borderline" difficulty band (0 < pass rate < 1). This added 4 borderline tasks, resulting in 17 tasks for Codex and 15 for Claude (two high-effort tasks were omitted for Claude due to budget constraints). The borderline calibration on Codex meant these tasks were not necessarily borderline for Claude.
*   **Evaluation (Tier-C):** Upon agent completion, test files from the gold PR diff were applied to the agent's workspace and executed against the agent's generated code. A task was considered "passing" if and only if all gold tests passed, adhering to the SWE-bench evaluation protocol where the agent does not see the test files.
*   **Safety and Isolation:** All agent runs were executed within an egress-locked pod environment. GitHub DNS was blackholed, Git remotes were scrubbed, credentials were stripped, and `git push`/`commit` commands were denied via `PATH` shims. Future commit history was pruned to prevent agents from accessing gold solutions.

#### 4.3 Independent Variable: Injection Strategy

The study employed three distinct context-injection strategies:
*   **NONE:** The `AGENTS.md` file was removed from the agent's workspace. No repository context was provided in the system prompt or made accessible to the agent.
*   **ALWAYS ON:** The complete content of the `AGENTS.md` file was injected into the system prompt at every turn, prefaced by a framing sentence. The `AGENTS.md` file was also removed from the workspace to prevent redundant reading.
*   **SELECTIVE:** Topic-organized wiki files (e.g., `wiki/architecture.md`) were placed in the workspace. The agent was provided a system-prompt hint to consult `wiki/*.md` and was able to retrieve relevant files on demand using its `Read` tool. A notable caveat: for `opshin`, the SELECTIVE wiki content matched the `AGENTS.md` file. However, for `pdm` and `firebase`, the SELECTIVE wiki was a broader, auto-generated repository wiki (approximately 10x and 18x larger, respectively), thus confounding delivery channel with context corpus for these two repositories. The authors note this as a known confound, asserting that the larger corpus would only strengthen the correctness null if no effect was observed.

#### 4.4 Agents

Two frontier coding agents were used:
*   **Claude Code (claude-sonnet-4-6, Anthropic):** A multi-turn, tool-use agent. Context was injected via `--append-system-prompt`. Runs were cost-capped at $6/run.
*   **Codex CLI (gpt-5.5, OpenAI, ChatGPT-plan auth):** A single-session agent. Context was injected by prepending it to the user prompt, as Codex lacked a dedicated system-prompt flag. Runs were turn-capped at 120 via a watchdog.
The difference in context injection channels (system prompt vs. user-turn prepend) was acknowledged as a confound for direct cross-agent comparisons, though within-agent strategy comparisons remained internally consistent.

#### 4.5 Dependent Variables

*   **Correctness:** Binary outcome (pass/fail) based on gold-test execution.
*   **Efficiency Metrics:**
    *   **Portable (comparable across agents):** Tool calls, wall-clock duration, total output tokens.
    *   **Agent-specific:** Cache-read tokens, cache-creation tokens (Claude only; Codex integrated cached input into its input token count). Turn counts were excluded as a cross-agent metric due to an artifact in Codex's event logging.

#### 4.6 Statistical Analysis

The unit of analysis was the task, with the three repeats averaged per (task, strategy) pair. Statistical methods included:
*   **Omnibus permutation test:** Strategy labels were permuted within-task (10,000–20,000 iterations) to test if strategy explained correctness beyond task difficulty, using the variance of marginal strategy pass-rates as the test statistic.
*   **Paired Wilcoxon signed-rank tests:** Applied for efficiency metrics, followed by Holm-Bonferroni correction for multiple comparisons (12 tests across 3 pairs × 4 metrics).
*   **TOST (Two One-Sided Tests) equivalence:** Used to establish bounded equivalence claims. Task-clustered bootstrap (10,000 iterations) was applied to paired strategy differences, with equivalence declared if the 95% confidence interval fell within ±δ.
*   **Monte Carlo power analysis:** Simulated binary outcomes under varying true effect sizes (∆) and task counts (n_tasks) to determine the minimum detectable effect (MDE) and required sample size for 80% power.

#### 4.7 Manipulation-Validity Probe

To address concerns about an potentially "inert manipulation," the study conducted a pre-registered manipulation-validity probe. This involved rating the quality of the three `AGENTS.md` files against a structured rubric (covering build/test/style, architectural guidance, specificity) used across a 40-repository corpus. Additionally, two "convention-closest" near-miss tasks (tasks with 1-4 failing gold tests, most likely to flip with additional information) were re-run under all three strategies, with 3 repeats per task on both agents (36 cells in total). The objective was to ascertain if the real, unmodified `AGENTS.md` could convert a near-miss failure to a pass.

### 5. Main Findings and Results

#### 5.1 Correctness: No Measurable Strategy Effect

*   **Overall Null Effect:** Neither Claude Code nor Codex demonstrated a statistically significant improvement in correctness based on the context injection strategy. For Claude, all pairwise strategy differences in pass rates were ≤2.3 percentage points (pp). For Codex, the largest difference was 5.9pp (NONE vs. SELECTIVE). The omnibus permutation tests yielded p-values of 1.000 for Claude and 0.66 for Codex, indicating no detectable strategy effect.
*   **Dynamic Range (Borderline Tasks):** The observed null effect persisted even when examining tasks within the "borderline" difficulty range (tasks with baseline pass rates between 17% and 67%). For 4 Codex-borderline tasks, NONE achieved 58% pass rate, while ALWAYS ON and SELECTIVE both achieved 42%, suggesting context injection did not improve performance even where an effect could potentially be detected.
*   **Equivalence Bounds:** Descriptive equivalence testing (TOST) on task-clustered bootstraps bounded every pairwise strategy difference to less than 10pp for Claude and less than 15pp for Codex. The observed point estimates were near zero.

#### 5.2 Efficiency: Narrow Process Signals, Otherwise Null

*   **Claude Specifics:**
    *   **Cache Efficiency:** The SELECTIVE strategy for Claude significantly reduced cache-creation tokens compared to NONE (p=0.001, Holm-corrected p=0.012), with 11 out of 11 tasks showing lower usage. This was attributed to the mechanical difference in how context is delivered (short retrieval hint vs. full `AGENTS.md` re-presentation).
    *   **Opshin Wall-Clock Time:** On the `opshin` repository, which contained explicit warnings about long test suite runtimes in its `AGENTS.md`, Claude's wall-clock time was approximately 24% lower under context-aware strategies (NONE: 2689s vs. ALWAYS ON: 2066s vs. SELECTIVE: 2032s). This reduction correlated with a dose-dependent decrease in blind full-suite test runs (NONE: 3.67 runs/cell; ALWAYS ON: 2.44 runs/cell; SELECTIVE: 1.67 runs/cell). This effect was categorized as an exploratory process effect rather than a correctness outcome.
*   **Codex Specifics:** All efficiency metrics for Codex (tool calls, output tokens, duration) remained flat across all strategies, with negligible effect sizes.
*   **Cross-Agent Comparison (Qualitative):** Qualitatively, Codex generally demonstrated leaner operations (fewer tool calls, less wall-clock time, fewer output tokens) but with a slightly lower pass-rate. This comparison was noted as confounded due to agent differences in injection channels, tokenizers, and token accounting.

#### 5.3 Agent-Specific Borderline Tasks

A significant finding was the variability in task difficulty across agents. For the 15 shared tasks, per-task pass rates showed a positive but imperfect correlation (Spearman ρ=0.75, p=0.001; Pearson r=0.77). This indicates that while difficulty generally transfers, the "informative band" (tasks where an intervention might show an effect) is agent-specific. Approximately 40% of the shared tasks were borderline for only one agent or exhibited different floor/ceiling status across agents. For example, `pdm#3790` was borderline for Claude but trivially difficult (0/3 passes) for Codex, while `pdm#3769` was borderline for Codex but trivially easy (3/3 passes) for Claude.

#### 5.4 Classifier Portability Lesson

During preliminary screening, the study's effort classifier (which classified tasks based on `turns≥30`) misclassified all Codex tasks as "trivial." This was due to Codex emitting only one `turn.completed` event per session regardless of actual work. Reclassification using tool calls, a portable metric, recovered genuinely high-effort tasks, highlighting that turn-based metrics may not be portable across different agent architectures.

#### 5.5 Power Analysis and Detection Limits

Monte Carlo simulations revealed that with the study's sample size (n=17 tasks, 3 repeats), even a large effect of ∆=30pp had only a 57% chance of being detected. Detecting a smaller effect of ∆=10pp with 80% power would require approximately 120-200 tasks. Increasing repeats from 3 to 10 for n=17 tasks only marginally improved power (13% to 58% for ∆=15pp). This indicates that task-level variance dominates, necessitating more unique tasks rather than more repeats to achieve higher statistical power for detecting smaller effects.

#### 5.6 Why the Null Holds: Skill, Not Knowledge

Analysis of near-miss failures (tasks with 1-4 failing gold tests) revealed that agent failures were predominantly attributed to implementation skill rather than a lack of repository knowledge that context files could supply.
*   **Task 510 (opshin):** Failed due to a correctness bug in a complex optimization pass, not missing facts.
*   **Task 907 (firebase):** Failed due to incorrect architectural pattern choice (reactive retry instead of proactive token refresh), not secret knowledge.
*   **Task 554 (opshin):** Failed due to miswiring a check for V2 validator arguments despite knowing the V3 rule.
*   **Task 593 (opshin):** Failed due to challenges in deep type-system reasoning.
These examples suggest that agents fail on aspects like feature design, pattern selection, and exact wiring, which are not typically addressed by general repository context files.

#### 5.7 Manipulation-Validity Probe Results

The manipulation-validity probe, designed to confirm that the `AGENTS.md` files were not inert, yielded several findings:
*   **Context File Quality:** The `AGENTS.md` files used were rated "Good" or "Excellent" against a structured rubric, indicating they were not low-quality or lacking content.
*   **No Helpful Flip:** The real `AGENTS.md` never converted a near-miss failure to a pass on either agent. For Codex, 18 out of 18 near-miss runs failed regardless of strategy.
*   **Non-Positive Trend (Claude):** For `firebase` task 907, which was borderline for Claude, the agent passed 2/3 runs under NONE, 1/3 under ALWAYS ON, and 0/3 under SELECTIVE. While not a general claim, this trend indicated that more context did not improve correctness in this specific instance, and no condition led to a flip towards passing.
*   **Agent-Specific Difficulty Confirmation:** Task 554 was observed to be "Claude-floored," further illustrating agent-specific difficulty.
The probe confirmed that the `AGENTS.md` content was capable of perturbing agent behavior (as seen in the `opshin` efficiency signal) but did not provide the implementation skill necessary to convert near-misses into passes.

### 6. Significance and Potential Impact

This research provides empirical evidence that challenges common assumptions about the efficacy of generic context files like `AGENTS.md` for AI coding agents. Its significance and potential impact span several areas:

*   **Reconciliation of Prior Contradictions:** The study offers a candidate explanation for the conflicting findings in previous research (Lulla et al., 2026; Gloaguen et al., 2026). It suggests that generic context files may not measurably improve correctness for either agent family, aligning with Gloaguen et al.'s findings. The efficiency gains reported by Lulla et al. might be attributable to mechanical costs of context injection (larger prompts, more tokens) rather than enhanced agent capability. The key insight that "borderline task difficulty is agent-specific" explains why single-agent studies might yield different conclusions if they drew tasks from different agents' informative performance bands.
*   **Practitioner Implications for Context File Authoring:** The primary finding—that generic context files, despite significant authoring effort and high quality ratings, do not measurably improve correctness (bounded to <10–15pp)—has direct implications for software development teams utilizing coding agents. It suggests that effort spent on crafting detailed `AGENTS.md` documents, in the naturalistic style-guide format used in this study, may not translate into improved code quality or functional correctness from the agent. Practitioners might instead consider prioritizing other strategies such as task decomposition, robust tooling, or example-driven prompting to enhance agent performance.
*   **Nuanced Understanding of Context Utility:** While correctness did not improve, the study did identify specific, narrow process-level benefits. For instance, the SELECTIVE strategy for Claude reduced cache-creation tokens, and context files on the `opshin` repository reduced wasteful full-suite test runs due to explicit warnings. This indicates that context can still offer value in terms of cost or latency optimization, influencing *how* an agent works even if it doesn't change the correctness outcome. This suggests a shift from expecting correctness improvements to potentially leveraging context for efficiency or process guidance.
*   **Insights into Agent Capabilities and Failure Modes:** The detailed failure-mode analysis reveals that current frontier coding agents often fail on higher-level implementation skills, such as feature design, architectural pattern selection, and precise wiring, rather than simply lacking repository-private facts. This suggests a fundamental limitation in current agent capabilities that cannot be easily overcome by simply providing more descriptive documentation. Future agent development might need to focus on enhancing these "implementation skills" directly.
*   **Methodological Contributions to Agent Evaluation:** The study makes several methodological contributions:
    *   It demonstrates the application of equivalence testing (TOST) in agent evaluation to establish bounded null effects.
    *   It highlights the critical importance of `agent-specific task screening` to ensure that ablation studies operate within an "informative dynamic range" where effects can actually be observed, rather than being obscured by floor or ceiling effects.
    *   The power analysis underscores that detecting small to moderate effects (e.g., 10pp) requires substantially larger task sets (120-200 tasks) than typically used in current research, emphasizing the need for scaled experimental designs.
    *   It reveals that certain common metrics, like turn counts, may not be portable across different agent architectures, advising caution in metric selection for cross-agent comparisons.
*   **Call for Future Research:** The study explicitly acknowledges limitations, including sample size, repository diversity, potential confounds (e.g., injection channel asymmetry, `SELECTIVE` corpus variations), and the naturalistic nature of the context files. These limitations delineate clear avenues for future research, such as investigating purpose-built, task-specific context, evaluating different languages or larger codebases, and designing experiments with higher statistical power to definitively confirm or refute smaller effects.

In conclusion, this research provides a rigorous, controlled investigation into the role of context files for AI coding agents. By demonstrating a bounded null effect on correctness and offering a mechanistic explanation for agent failures, it offers valuable insights for both practitioners and researchers, suggesting a redirection of effort towards enhancing fundamental agent capabilities and optimizing process-level interactions rather than solely relying on generic descriptive context.
