### 2. How This Work Fits into the Broader Research Landscape

The work addresses a perceived shift in the development of coding agent systems from "harness engineering" to "loop engineering." Harness engineering refers to the ability of agents to solve localized, self-contained coding tasks, typically judged by a final correct output. Loop engineering, in contrast, involves managing sustained, long-horizon software development, where agents must govern execution across complex task structures, maintain state continuity, and manage regression pressure as dependent work accumulates over extended periods. Examples of this shift include goal modes and dynamic workflows in frontier coding agents like OpenAI's Codex and Anthropic's Claude Code.

Existing coding benchmarks, such as SWE-bench (Jimenez et al., 2023a) and its variants (Zan et al., 2025; Yang et al., 2024c; Liu et al., 2025), primarily focus on repository-level issue resolution or feature implementation (Zhou et al., 2026; Chen et al., 2025; Thai et al., 2025). These benchmarks are often "terminal" in design, evaluating an agent based on the final success of a patch or solution. While some "long horizon" benchmarks exist (Kwa et al., 2025; Ding et al., 2025), they generally do not expose intermediate development units, explicitly track accumulated obligations, or make the execution order observable in a diagnostically meaningful way. This design limits the ability to assess an agent's capacity to preserve intermediate work, avoid regressions, or follow an effective sequence through dependent subproblems.

LOOPSBENCH positions itself as a benchmark specifically tailored for loop engineering evaluation. It aims to fill the gap by providing a framework that explicitly represents tasks as dependency graphs of separately testable development units, incorporates a flow-aware runtime that enforces regression obligations, and records loop traces to diagnose agent behavior over time. This approach shifts the evaluation focus from mere end-state outcomes to the continuous process of sustained software development and the underlying "loop state discipline" of coding agents.

### 3. Key Objectives and Motivation

The primary objective of this research is to introduce LOOPSBENCH, a benchmark designed to evaluate coding agents within the context of sustained, long-horizon software development, focusing on the principles of "loop engineering."

The motivation for LOOPSBENCH stems from several key observations regarding the current state of coding agents and existing evaluation methodologies:

*   **Emergence of Long-Horizon Software Development Agents:** Modern coding agent systems are increasingly designed to handle complex, multi-step software development tasks that extend over long horizons. These systems require mechanisms to maintain persistent objectives, manage progress criteria, and distribute work across extended execution sessions. The core challenge for these agents shifts from merely generating correct code for isolated problems to effectively managing the entire software development lifecycle within a continuous "loop."
*   **Limitations of Terminal-State Benchmarks:** Current benchmarks largely assess an agent's ability to produce a correct final output for a given task or issue. They do not adequately capture the intermediate processes, decisions, and state management crucial for long-horizon work. Specifically, existing benchmarks:
    *   Do not reveal whether an agent preserves intermediate obligations or adheres to a viable sequence of dependent subproblems.
    *   Provide limited insight into an agent's ability to avoid regressions as a codebase evolves and dependent work accumulates.
    *   Lack mechanisms to observe the execution order and the agent's internal "planning" or "routing" decisions when faced with interdependent tasks.
*   **Need for Diagnostic Evaluation:** To understand and improve loop-based coding agents, a diagnostic evaluation framework is necessary. Such a framework should:
    *   Expose intermediate "development units" as separately testable components.
    *   Track accumulated obligations, ensuring previously completed work remains valid throughout the development process.
    *   Make the agent's execution order and adherence to dependencies observable.
*   **Evaluating "Loop State Discipline":** The research aims to provide a benchmark that measures how an agent maintains its plan, code, and test state across prolonged execution, rather than just its capacity for per-unit code generation. This includes assessing planning fidelity, implementation characteristics (e.g., patch efficiency), and testing practices (e.g., regression protection).
*   **Source-Grounded and Diverse Tasks:** The motivation also includes grounding tasks in authentic, real-world development scenarios (PR sequences, course labs, research evolutions) to ensure relevance and capture diverse dependency structures and development challenges.

In summary, LOOPSBENCH seeks to establish a contract for evaluating the "loop engineering" capabilities of coding agents, providing detailed diagnostics on their ability to manage complex, sustained software development tasks beyond isolated problem-solving.

### 4. Methodology and Approach

The LOOPSBENCH methodology involves a multi-stage pipeline for constructing and evaluating long-horizon coding tasks, designed to expose "loop engineering" challenges.

#### 4.1. Benchmark Design Principles

*   **Dependency DAGs:** Each task is represented as a Directed Acyclic Graph (DAG) where nodes are source-grounded, separately testable development units. Edges represent prerequisite relations between these units.
*   **Flow-aware Evaluation Runtime:** The runtime dynamically releases tests for units as their prerequisites are met (the "ready frontier"). Importantly, completed units' tests are retained as "regression obligations" throughout the agent's execution, meaning passing previously completed tests is required for overall success.
*   **Loop Trace Diagnostics:** The system records a "loop trace" of the agent's execution, allowing for detailed analysis of its planning, implementation, testing, and state management behaviors.

#### 4.2. Task Construction Pipeline

The construction process involves five numbered stages:

1.  **Task Collection:** Authentic, real-world source artifacts are gathered from three categories:
    *   **Course Labs (112 projects):** Collected from 30 university homepages and GitHub mirrors, including handouts, skeleton code, and instructor tests. These typically have clear modular structures.
    *   **PR Sequences (148 candidates):** Full commit histories and merged pull request (PR) streams from 56 actively maintained GitHub repositories. These provide rich, real-world dependency chains.
    *   **Research Evolutions (47 candidates):** 212 papers from 48 venues, focusing on highly cited papers with open-source implementations. A Claude Code-based classification identifies "load-bearing inheritance edges" to form clusters of related research work.

2.  **Task Preprocessing:** Collected artifacts are normalized into atomic candidate tasks with a uniform evaluation contract.
    *   Course Labs: Handouts are unified, and scattered skeleton files are reorganized.
    *   PR Sequences: Repositories are cloned, per-PR diffs extracted, and Claude Code is used to aggregate segments validated against fixed acceptance standards.
    *   Research Evolutions: Papers are clustered based on load-bearing citations.
    *   Native test runners are wrapped behind a uniform entry point to standardize execution.

3.  **Task Selection:** Candidate tasks are filtered based on two source-agnostic thresholds to ensure sufficient complexity for long-horizon evaluation:
    *   **Temporal Span:** Minimum 2.5 months (e.g., project duration, PR merge interval, publication date span).
    *   **Solution Scale:** Minimum 1,200 units (using a source-specific scale metric).
    *   This process yields 112 tasks for the final benchmark suite.

4.  **Development Unit Definition and Intra-Task Relation Recovery:**
    *   **Development Unit (u):** Defined as `(r_u, s_u, p_u, Δ_u, T_u)` – requirement, file/symbol scope, prerequisite set, reference patch contribution, and standard tests. Unit boundaries align with source provenance (e.g., merged PRs, modules, methodological increments).
    *   **Dependency DAG Formalization:** Each task is formalized as a DAG over its development units. This DAG serves as an evaluation contract, not necessarily an optimal development path.
    *   **Prerequisite Patterns:** Four patterns are admitted with unambiguous evidence: sequential PR chains, structural module reuse, functional producer-consumer API edges, and compositional layering (e.g., subclass extension).
    *   **Evidence for Edges:** Requires hunk overlap on the same file or symbol-level dependence (import, call, subclass). A denylist excludes spurious chains from common files (e.g., hot monoliths, generated artifacts).
    *   **Ready Frontier (`R_t`):** The set of nodes whose tests have not yet passed but all their predecessors have completed.

5.  **Task Instrumentation:** Selected candidates are transformed into self-contained evaluation instances.
    *   **Instruction Formalization:** A Claude Code-based recovery step (using Claude Opus 4.7) generates a single acceptance instruction from the gold diff, removing implementation details and retaining the public contract. Identifying repository, course, or author information is stripped.
    *   **Environment and Test Suite Synthesis:** A Claude Code-based process traverses the source frame to collect runtime dependencies and writes a Dockerfile (and optionally `docker-compose.yaml`).
    *   **Test Materialization:** The pipeline traverses the DAG topologically. At each unit `u`, it drafts missing tests, applies `u`'s gold patch, and runs tests under a three-trial check:
        *   **Solvability:** Full gold solution makes all tests pass.
        *   **Non-triviality:** Empty workspace makes no new tests pass.
        *   **Discriminativeness:** Gold solution restricted to `u`'s ancestors still leaves at least one test failing.
    *   Units with environment or suite issues are discarded.

#### 4.3. Evaluation Protocol

*   **Input Visibility:** The evaluated loop receives task instructions and per-unit requirement bundles (plain files). Gold solutions and ready unit identities are withheld.
*   **Topologically Gated Test Release:** Tests are released layer-by-layer along the dependency DAG. A gate node `v` joins the ready frontier after all predecessors are in `C_t` (completed tests).
*   **Regression Obligations:** Once a unit clears its gate, its tests and those of its predecessors remain enforced as regression tests for all subsequent layers, making "Regression Rate" a direct metric.
*   **Dual Container Snapshot Pipeline:** A two-container system separates agent execution (Container A, write target) from test adjudication (Container B, reads snapshots from A). The evaluation runtime periodically samples Container A, diffs changes, and runs the released test suite in Container B. This enables recording loop trace metrics at actual change points.

#### 4.4. Metrics

The evaluation protocol yields several metrics:
*   **Resolve Rate (RR):** Percentage of tasks where all released tests pass at task end.
*   **Test Pass Rate (TPR):** Average fraction of released tests passing at task end.
*   **Dependency Depth (Depth):** Normalized deepest layer reached before the first residual handoff.
*   **Regression Rate (Reg):** How often previously passing tests fail at a later point.
*   **Tokens (Tok):** Total tokens consumed per task.
*   **Planning Fidelity (Table 3):** Edge F1, Layer ρ, Critical Path Ratio (CPR), Width Ratio (WR) compare recorded plans to source DAGs.
*   **Implementation (Table 3):** PatchLen (ratio of generated patch lines to gold), Jacc (token-level Jaccard distance).
*   **Testing (Table 3):** #T (number of agent-authored tests), F2P (fail-to-pass yield of agent tests).
*   **Loop Trace Metrics (RQ3):** Rounds (context-budget rounds per run), Reg/run (regression events per run).

### 5. Main Findings and Results

The experiments were structured around three research questions concerning loop engineering in coding agent evaluation.

#### 5.1. RQ1: How Far Do Coding Agent Loops Sustain Progress?

*   **Overall Performance:** Across various models and loop implementations, the strongest configuration, Opus-4.7 paired with Claude Code and outer continuation, resolved **25.00%** of LOOPSBENCH tasks. All evaluated configurations remained significantly below full resolution.
*   **Model Performance (within family with vendor loops):** A clear monotonic trend in Resolve Rate (RR) was observed with model scaling. For example, within the Claude family, Opus-4.7 achieved 25.00% RR, while Sonnet-4 achieved 7.14%. Similarly for GPT and Qwen families, stronger models showed higher RR. This trend was preserved when evaluated with pass@3, indicating robustness beyond single-trial variance.
*   **Loop Implementation Performance (fixed model: gpt-5.4):** Different loop implementations yielded varying Resolve Rates, with Codex (18.75% RR) and Claude Code (17.86% RR) outperforming open-source alternatives like OpenHands (9.82% RR) and SWE-agent (8.93% RR).
*   **Impact of Continuation:** Without the outer evaluation loop (i.e., single continuous execution), agents typically reached only a shallow dependency prefix. External continuation mechanisms were found to reduce early stalls and increase partial progress.
*   **Long-Horizon Limitations:** The results suggest that limitations are not solely attributable to model choice or loop implementation in isolation. Instead, long-horizon challenges appear to stem from loop-level obligations, such as maintaining a global plan, ensuring residual continuity, and robustly retaining regression obligations.
*   **Per-Source Resolve Rate:** PR Sequences were consistently the most challenging task source (maximum 3.45% RR), indicating particular difficulty with obligation retention across complex, inter-dependent edits. Course Labs accounted for the majority (≥70%) of resolved tasks, likely due to their comparatively shallower dependency depth and clearer modular decomposition.

#### 5.2. RQ2: How Do Coding Agent Loops Maintain Plan, Code, and Test State?

This question was addressed through analysis of recorded loop traces, comparing agent behavior to the source-recovered prerequisite DAG.

*   **Planning Fidelity:**
    *   **Internal Dependency Gap:** Evaluated loops recovered only partial dependency structures. Edge F1 (exact prerequisite edge recovery) and Layer ρ (topological layer correlation) showed imperfect agreement with the source DAG across all loops (e.g., Claude Code: Edge F1 0.71, Layer ρ 0.65; OpenHands: Edge F1 0.39, Layer ρ 0.33).
    *   **Concurrency Budget:** Closed-source loops (e.g., Claude Code, Codex) tended to organize execution with a more concurrent, tree-shaped structure, aligning closer to the concurrency budget implied by the reference DAG (Width Ratio (WR) between 1.08 and 1.83). Open-source loops (e.g., OpenHands, SWE-agent) often formed near-chains (WR between 0.24 and 0.39), suggesting over-serialization of tasks. Critical Path Ratio (CPR) was notably higher for open-source implementations (0.85-0.97) compared to closed-source ones (0.31-0.41), confirming a more linear execution flow.
*   **Implementation:**
    *   **Patch Surplus:** Candidate patches generated by agents for resolved units consistently exceeded the length of the gold reference patches (e.g., PatchLen of 1.58 for Claude Code, 2.31 for OpenHands). Token overlap with gold (Jaccard similarity) remained moderate (e.g., 0.62 for Claude Code, 0.73 for OpenHands). This suggests that agent-generated patches were often longer due to factors such as uniform style application, added comments, or rewriting existing repository blocks, potentially reflecting incomplete loop state rather than fundamentally different implementations.
*   **Testing:**
    *   **Maintenance Gap:** Loop traces revealed sparse test authoring by agents as long-horizon work progressed, leading to limited agent-authored regression protection for earlier obligations. The number of tests authored (#T) was consistently lower than the native suite (e.g., 28 for Claude Code, 16 for OpenHands).
    *   **Regression Events:** Deployed loop implementations exhibited noticeable regression rates (e.g., Claude Code: 7.11%, OpenHands: 2.46%), indicating a degradation of previously satisfied obligations over time. Configurations with very low Resolve Rates showed lower apparent regression rates, but this was attributed to a limited set of passing obligations available for measurement, not necessarily better retention.

#### 5.3. RQ3: Which Loop Engineering Factors Shape Long Horizon Execution?

This question investigated objective persistence, residual routing, context renewal, and regression pressure across different loop implementations.

*   **Context Renewal:** Dynamic workflows recorded the highest number of context-budget rounds per run (97.96), followed by Claude Code goal mode (34.69), Codex goal mode (32.76), and the Ralph loop (13.24). The dynamic workflow configuration also achieved the highest Resolve Rate (24.11%), while Ralph reached 7.84%. This suggests that differing context renewal strategies influence overall task resolution.
*   **Regression Persistence:** Despite varying context renewal strategies, regression events remained visible across all four loop profiles. Dynamic workflows recorded 0.36 regression events per run, Codex goal mode 0.34, Claude Code goal mode 0.13, and Ralph 0.17. This indicates that distributing work across narrower worker contexts, while potentially improving overall resolution, does not eliminate the need for explicit state tracking to preserve completed obligations.

### 6. Significance and Potential Impact

LOOPSBENCH represents a development in the evaluation of coding agents by shifting the focus from terminal-state outcomes to the intricate challenges of "loop engineering" in long-horizon software development.

The significance and potential impact of this work include:

*   **Establishing a New Evaluation Paradigm:** By formalizing long-horizon tasks as dependency DAGs, implementing a flow-aware runtime with gated test release and persistent regression obligations, and recording detailed loop traces, LOOPSBENCH introduces a framework for measuring aspects of coding agent performance previously undiagnosed. This enables a more comprehensive assessment of agents' abilities in sustained, real-world development scenarios.
*   **Diagnostic Insights into Agent Limitations:** The findings reveal significant limitations of current frontier LLMs and their associated loop implementations in managing complex, long-horizon tasks, with the strongest configuration resolving only 25.00% of tasks. The diagnostic traces provide specific insights, pointing to deficiencies in global plan maintenance, effective residual work routing, state continuity across iterations, and robust regression obligation retention. These insights can guide future research and development efforts.
*   **Guiding Future Agent Development:** The research provides empirical evidence that attributing performance solely to model choice is insufficient. It highlights the critical role of "loop engineering" factors in shaping long-horizon execution. This suggests that future advancements in coding agents will require a joint focus on improving core LLM capabilities and enhancing the surrounding loop mechanisms, particularly in areas like structured state management, persistent objective tracking, and robust regression prevention.
*   **Promoting Reproducibility and Community Research:** By open-sourcing the benchmark data and code, including all 112 tasks, over 5,300 development units, and executable tests, LOOPSBENCH provides a standardized, reproducible platform. This fosters collaborative research in an evolving field, allowing other researchers to evaluate new models and loop implementations against a common, challenging set of tasks.
*   **Informing Infrastructure Design:** The analysis of different loop implementations and their impact on context renewal and regression events offers practical implications for designing more robust and efficient coding agent infrastructure, especially concerning how agents manage context, coordinate subtasks, and track evolving project state.

While acknowledging limitations such as the conservative nature of the recovered DAG, potential biases in task materialization, and the scope of tested project types, LOOPSBENCH contributes a tool for understanding and advancing the capabilities of autonomous coding agents in complex, real-world software engineering contexts.
