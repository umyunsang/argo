# 제공 PDF 기준 정정 및 연구–프로토타입 요구사항

## 최우선 관계 — 사용자 명시 교정

**졸업논문 연구와 NAIS_AI는 독립 과제가 아니다. 졸업논문 연구가 ARGO의 설계를 도출·비교·검증하는 선행 연구이며, 그 결과를 구현한 ARGO가 NAIS의 후행 프로토타입이 되는 하나의 연쇄 작업이다.**

문헌과 유사 실험 분석 → 구성요소·연결 방식·제어 정책의 설계 대안 → 가설·실험·비교로 선택 근거 확보 → 검증 범위를 명시한 ARGO 통합 설계 → 허용된 단계의 native 구현 → NAIS 시연·현장 검증 → 구현 관측을 연구 계보로 환류하는 경로를 유지한다.

아래에서 연구 지표와 제품 acceptance, 문서의 역할, 현장 개발 시기를 구분하는 것은 **동일 연구의 서로 다른 증거와 단계**를 구분하는 것이다. 서로 무관한 논문 benchmark와 별도 해커톤 demo를 만들라는 뜻이 아니다. 논문 연구의 선택·기각 결과가 실제 prototype 구성에 반영되지 않으면 연결이 완료된 것이 아니다.

핵심 scientific-decision 실험은 통합 설계의 중요한 불확실성을 검증하는 수단이지 전체 논문 목적을 좁은 graph 실험 하나로 바꾸는 수단이 아니다. 기존 네 산출물은 모두 이 동일한 thesis→ARGO→NAIS 계보의 일부다. 현재 최우선 산출물은 prototype에 선행할 근거 있는 통합 연구설계와 그 선택을 검증할 실험이다.

## 적용 범위

2026-09-05에 사용자가 직접 지정한 세 PDF를 기준으로 앞선 방향 검토의 문서별 사실을 정정한다. 원본 PDF를 변경하지 않았으며 신청자·팀원의 연락처, 생년월일, 학번, 서명을 복사하지 않았다. 이 문서는 연구 작업 기록이며 새 실험·개발·외부 제출의 승인이 아니다.

세 문서는 같은 연구의 다른 조건을 제공한다. 졸업논문계획서는 ARGO 구축에 선행할 연구 목적·방법, 제공 신청서는 그 연구가 도달해야 할 제품 동작·구현 약속, 모집 공고는 그 제품을 현장에서 구현·평가·제출하는 요건이다. 현재 실행 승인과 native construction pause는 현행 프로젝트 authority를 따르며, 이를 연구 목표의 분리로 해석하지 않는다.

## 연구 목적과 제품 동작 연결

| 근거 | 보존할 목적·약속 | 연구/시연에서 관찰할 것 |
|---|---|---|
| THESIS p.1 | 문제·가설·조건·방법·지표·중단 규칙의 자율 선택 | 선택지·채택 이유·반례·구분 예측·관측 후 결정 |
| APP p.2 | 독립 노드의 병렬 검증과 같은 기준의 경쟁 | 동일 비교 조건 아래 실제 실행한 둘 이상의 후보와 결정 기록 |
| APP p.2 | 가지 확장·접기, 실패 이유 보존 | 살아남은 방향과 접힌 방향, 근거·결과·재개 조건 |
| APP p.2 / THESIS p.1 | 결과가 기획을 바꾸는 폐루프 | 한 번 이상의 관측 기반 후속 설계 변경; 각 변경의 출처 |
| THESIS p.1 / APP p.4 | 다른 agent 인계와 재확인 | 새 context에서 graph와 receipt만으로 다음 행동·금지 이유 복구 |
| NOTICE p.5 | 구현된 프로토타입과 발표의 일치 | 실제 동작·관측·발표 claim의 대응, 계획/미실행 표시 |

따라서 같은 연구 계보 안에서 논문의 최소 decision episode가 어떤 prototype 설계 결정을 검증하는지 연결하고, 그 결정이 본선의 실제 병렬 후보·경쟁 동작으로 이어짐을 확인한다. 기존 제안의 '두 설계·한 실행'만 시연한다면 신청서의 실제 병렬 검증·실험 경쟁까지 구현했다고 말할 수 없다. 최소 제품 시연은 둘 이상의 실제 실행 후보, 비교, 이유 있는 접기, 한 번의 결과 기반 다음 결정, 인계 경로를 포함하는 것을 제안한다. 이는 별도 demo 연구가 아니라 선행 연구로 선택한 기제의 구현 acceptance다. 현재 구현/효능이 확인됐다는 뜻은 아니다.

## 명세 충돌을 해결할 방법

### 1. 비교 가능성과 요소 제거 실험

APP pp.3–4의 '하네스가 다른 두 결과는 비교 불가'를 절대 규칙으로 구현하면 THESIS p.1의 구성요소 제거 비교를 스스로 금지한다. 동일 조건 결과를 무분별하게 합치지 않는 provenance 규칙과, 사전 명세된 처리군 차이를 비교하는 실험 규칙을 분리한다.

**제안 계약:** task/data/split/scorer/opportunity/budget 등 비처리 조건을 고정하고, 허용된 treatment 차이와 각 조건의 code hash를 사전 등록한다. 미등록 차이는 비교 불가, 명시된 처리 차이는 그 비교 목적에 한해 허용한다. 총 코드 해시가 다르다는 이유만으로 제거 실험을 탈락시키지 않는다.

### 2. 구체적 구현안과 검증된 설계의 구분

APP p.3은 Prime fork가 session/worker/kernel을 소유하고, LangGraph StateGraph/SqliteSaver가 graph 상태를, append-only journal이 evidence를 다루는 삼평면 설계를 제시한다. 현재 신청서 내용을 누락하거나 막연한 wrapper로 요약하지 않는다.

다만 LangGraph, 깊이 우선 frontier, 특정 interrupt/Command 방식이 논문으로 검증된 최선이라는 뜻은 아니다. 기존 native ownership과 중복되지 않는 interface·정합성·복구·비용을 비교하고 채택/변경 이유를 기록한다. 이 문서로 LangGraph 도입이나 native 이식을 즉시 실행하지 않는다.

### 3. 원본의 주장과 현재의 검증 상태

APP p.2의 '최근 연구 agent는 한 번 통과로 끝난다'는 포괄적 배경 설명은 앞서 검토한 경쟁 연구와 대조해 현재 논문/발표에서 좁혀 써야 한다. THESIS p.1의 '예비 실험 완료' 또한 현재 유효한 효능 증거가 확보됐다는 뜻으로 승격하지 않는다. 원본은 보존하고 후속 문서에서 검증 범위와 수정 사유를 밝힌다.

## 후속 작업과 인계

앞선 네 산출물의 요구사항을 보완하며 새로운 거대 framework를 추가하지 않는다. 각 requirement에 `source_id`, `sha256`, `page`, `explicit_or_interpretation`, `applies_to`, `design_decision`, `implementation_evidence`, `verification_status`를 연결한다. 논문 실험의 관측 → 채택/기각한 설계 결정 → native owner/interface → 후행 구현 증거 → 본선 제품 acceptance를 같은 graph에서 추적한다. 연구 선택 지표와 제품 acceptance의 종류는 구별하되 서로 분리된 프로젝트로 만들지 않는다. 원본 신청자 정보는 graph에 넣지 않는다.

과거 신청서의 시간 계획을 현재 APP의 요구사항으로 참조하는 연결은 supersede한다. 공고 p.3의 배점과 p.5의 개발/제출 요건은 실제 활성 문서·graph의 소비 경로에 연결하도록 Prime에 요청한다. 문서를 읽거나 전달한 것만으로 이 graph 반영이 완료됐다고 보고하지 않는다.
