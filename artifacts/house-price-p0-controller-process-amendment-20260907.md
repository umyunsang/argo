# House Price P0 실행 프로세스 변경안

상태: **제안 — 사용자 확인 전. 실제 P0 미실행.**

## 필요한 이유

원래 A안의 평가 controller는 별도 Prime daemon worker와 JSON 스트림을 사용한다. 실제 모의 검사에서 131,072자 도구 입력 하나가 1,299,174,268바이트의 반복 스트림 출력을 만들었다. 표준 이벤트 훅은 비동기 큐 뒤에서 처리되므로 하드 상한이 아니며, daemon 경로에서 텍스트 출력만 선택해도 내부 전송량은 제한되지 않는다.

## 권장 A2: 기존 Prime의 공개 진입점을 직접 실행

작은 과제용 진입점에서 공개 `main()`을 호출한다. 같은 Prime 0.9.2의 AgentSession·모델·인증·자원 로더·세션 기록·여섯 도구를 유지한다. 별도 엔진이나 daemon을 만들지 않고 네이티브 파일도 수정하지 않는다. 생성 코드는 계속 제한된 Docker에서 실행하며, 과학 실행 상태는 ORX만 소유한다.

달라지는 점:

- 평가 controller의 daemon worker·재연결·자동 복구를 사용하지 않는다. Root가 직접 실행 핸들과 종료를 관리한다.
- 표준 출력은 최종 텍스트만 받는다. 완료된 메시지·도구 결과·사용량은 Prime의 기본 세션 JSONL로 보존한다. 원래의 실시간 전체 스트림과 동일한 관측 방식은 아니다.
- 기존 Python kernel 하위 프로세스가 시작될 수 있다. 검증된 기존 interpreter를 고정하고 하위 프로세스 정리도 시험한다.
- 파일 크기·CPU·벽시계 시간 제한을 따로 검증한다. **macOS 메모리는 하드 상한이 아니라 주기적 감시와 초과 시 종료 정책으로만 취급한다. 순간 초과 가능성이 남는다.**

후보 수치: provider timeout 120초·retry 0, controller 단계별 wall 60분, 프로세스별 CPU 600초, 파일별 8MiB, RSS 감시 기준 2GiB/250ms. 이 값은 검증 전 제안이며 전체 프로세스 트리·디스크·메모리 하드 상한을 뜻하지 않는다. 실제 코드·환경과 함께 동결하기 전에 실패 우선 검사와 독립 검토가 필요하다.

## 대안

controller 메모리까지 반드시 OS 하드 상한으로 제한해야 한다면 현재 P0는 보류한다. Linux cgroup 등 전체 controller 격리 경계를 별도로 설계·검증해야 한다. 추가 환경·인증 범위를 승인된 것으로 가정하지 않는다.

## 확인할 결정

**이번 제한된 P0에 A2와 메모리 감시 방식의 한계를 허용할지**, 아니면 **controller 전체의 메모리 하드 상한 요구를 유지할지** 선택한다.

기존 House Price 선택·데이터·P0 시작·A 신뢰 범위 승인은 유지한다. 이 질문은 새로운 실행 구조와 자원 제한의 성격에 관한 것이다. A2 승인 자체가 검증 통과나 즉시 실행을 뜻하지 않는다. 실제 학습·숨겨진 채점은 아직 0회다.
